# Nested collection indices in schema errors — implementation notes

Issue: "validator: nested collection indices are lost in schema errors".

Injection scenario: the second element of a `Vec` fails field validation and
schema (struct-level) validation at the same time. After the error trees are
merged, the schema error either overrode the field error or ended up detached
from the element index.

## Root cause

Collections (`Vec`, sets, arrays, maps) implement `Validate` by returning
their `ValidationErrorsKind::List` under a made-up `_tmp_validator` key,
because a `ValidationErrors` can only map string keys to error kinds. That
marker has to be stripped exactly once, at the boundary where the collection
is attached to a named field path. Two boundary defects made the marker leak
into the public error tree and its JSON serialization:

1. `ValidationErrors::merge` did not strip `_tmp_validator` (only
   `merge_self` did), so a collection merged through the public combinator
   produced `items._tmp_validator.<index>.<field>` instead of
   `items.<index>.<field>`.
2. Multi-layer collections (`Vec<Vec<T>>`) wrap one marker per layer, but
   only the outermost was stripped, so inner layers leaked
   `items.<i>._tmp_validator.<j>.<field>`.

In both shapes the element's `__all__` schema error (and every other error of
that element) was detached from its real `field[index]` path.

## Options considered and final tradeoffs

### 1. Schema errors: attached to the container or to the element?

- **Hoist to the container** (`items.__all__` or top-level `__all__`):
  rejected. It loses the element index — the bug being fixed — and collides
  with the container's own schema errors under the same `__all__` key.
- **Disguise as a field of the container**: rejected for the same reason; it
  would also fabricate a field that does not exist on the parent struct.
- **Keep at the element** (`items.<index>.__all__`): chosen. The schema error
  is generated by the element's own `validate()`, so the merge step only
  attaches paths and never re-homes errors. `__all__` remains the key for
  struct-level errors, so old serialization keys are unchanged.

### 2. Structure for duplicate codes

- **Deduplicate by code**: rejected. It silently drops errors and changes the
  meaning of `Vec<ValidationError>`.
- **Keep every occurrence**: chosen. Field errors stay an ordered
  `Vec<ValidationError>` per field, so two validators emitting the same code
  on one field, and the same code at different list indices, remain
  distinguishable by position (`field` → ordered list, `items.<index>` per
  element). Custom `code = "..."` overrides flow through unchanged.

### 3. Compatibility with the old error JSON

- **Change top-level key types** (e.g. switch `ValidationErrors` to an
  ordered map): rejected. It would break the public API
  (`ValidationErrors(pub HashMap<...>)`) for no functional gain.
- **Keep every public key; only stop leaking the internal marker**: chosen.
  `ValidationErrorsKind::List` now holds
  `BTreeMap<usize, Box<ValidationErrorsKind>>` so a list element can itself
  be a list. Because the enum is `#[serde(untagged)]`, single-level trees
  serialize byte-identically to before (element struct errors still serialize
  as the bare field map), and old JSON documents deserialize into the new
  types unchanged. The only removed key is `_tmp_validator`, which was an
  internal implementation detail, never a stable serialization key.

### 4. Where the fix lives

The fix is concentrated in error path composition inside the `validator`
crate (`ValidationErrors::{merge, merge_self, merge_all, into_kind}` and the
collection `Validate` impls), not in the derive macro. The derive keeps
generating the same call graph for `nested`, `schema`, `range`, `length`,
`email`, `custom`, etc.; no test-specific special cases were added. No global
or thread-local state is involved, and the default configuration
(`skip_on_field_errors = true`, field-validations-take-priority) keeps its
previous semantics.

## Determinism

`ValidationErrors` wraps a `HashMap` with a random state, so JSON object key
order is not part of the stable contract. Regression tests therefore compare
the full typed tree (`PartialEq`) and the serialized `serde_json::Value`
(order-insensitive), and assert byte-stability of repeated serialization of
the same tree. The test suite uses no threads, no clocks and no random
inputs, so merge-order reversal mutations are checked by explicit
construction rather than fuzzing.

## Verification evidence

Commands (nightly toolchain, because `--all-features` enables the
nightly-only `derive_nightly_features` feature):

```
cargo fetch --locked
cargo +nightly test --locked --workspace --all-features
```

Result: 228 passed, 0 failed (validator, validator_derive,
validator_derive_tests, doc-tests).

Regression coverage:

- `validator/tests/errors_merge.rs` — public merge combinators: collection
  errors attach to `field[index]`; `merge_all` keeps field and `__all__`
  errors at the element index and preserves nested list kinds; multi-layer
  collections keep indices; empty collections produce no errors; duplicate
  codes preserved in order; merge-order reversal yields the identical tree;
  serialization is stable and never contains `_tmp_validator`.
- `validator_derive_tests/tests/nested_schema_errors.rs` — the injection
  scenario end to end through the derive: full-tree and JSON equality for a
  failing second `Vec` element, `Option<Vec<_>>`, empty `Vec`, multi-layer
  `Vec<Vec<_>>`, custom and duplicate codes, `#[serde(rename)]` fields, and
  the merge-order reversal mutation.
- Negative assertions in both suites: no top-level `__all__` for element
  schema failures, the container key is a `List` (never a `Field`), valid
  elements are absent from the tree, and the internal marker key never
  appears in serialized output.
